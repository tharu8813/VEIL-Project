# 07. 암호화 다운로드 금고

## 제품 행동 [확정]

사용자는 일반 브라우저처럼 링크를 눌러 파일을 다운로드한다. VEIL은 파일을 보호된 금고에 저장하고 Ctrl+J에서 상태·파일명·열기·내보내기를 제공한다. 영구 파일의 평문은 **사용자가 선택한 내보내기**에서만 외부 일반 폴더에 생성한다.

## 보안 불변 조건

- 다운로드 완료 후 `%Downloads%` 같은 평문 임시 파일을 다시 암호화하는 접근은 최종 구현으로 불합격.
- 파일 내용뿐 아니라 원래 이름·원본 URL·콘텐츠 형식·시간 등 민감 메타데이터도 암호화한다.
- 암호화 실패·저장소 부족·스트림 가로채기 실패 시 보호되지 않은 디스크 경로로 자동 변경하지 않는다.
- 금고 저장 파일을 열거나 삭제할 때 파일 식별자·경로·확장자를 신뢰하지 않는다.
- 다운로드 출처와 파일의 신뢰성을 동일시하지 않는다. 악성 파일 검사·경고·샌드박스 정책을 별도로 검토한다.

## 다운로드 파이프라인 가설

```text
브라우저 다운로드 이벤트
  → 실제 응답 데이터에 접근 가능한 어댑터 [엔진별 검증 필요]
  → authenticated streaming encryption
  → 임시 암호문 객체(원자적 쓰기)
  → 무결성 확인 및 암호화 인덱스 등록
  → Ctrl+J 목록에 완료 표시
```

Qt WebEngine의 `QWebEngineDownloadRequest`는 다운로드 위치 제어 기능이 있으나 응답 데이터를 바로 암호화 스트림에 전달하는 API가 있는지 별도 검증이 필요하다. 일반 HTTP 요청만 별도 HTTP 클라이언트로 재요청하면 쿠키/서비스 워커/Blob 등과 동등한 의미가 성립하지 않을 수 있다.

WebView2에서는 실험 런타임 옵션을 켜고 일반 다운로드를 취소한 합성 GET의 본문을 메모리에서 얻었다. 시험은 작은 응답 한 건의 해시를 비교했다. 크기 한도, 인증·POST·Blob·Service Worker 응답, 원본 기록 경로는 후속 실측 대상이다. [Phase 0 결과](phase0-evidence.md)

## 테스트할 다운로드 유형

| ID | 유형 | 수용 기준 |
|---|---|---|
| D-01 | 일반 HTTP/HTTPS GET | 원본 평문 일반 디스크 기록 없이 금고 저장 |
| D-02 | 인증 쿠키 포함 | 기존 로그인 상태와 동등하게 다운로드 |
| D-03 | 리다이렉트 및 POST | 요청 방식/인증/헤더/본문 의미 보존 |
| D-04 | Blob/Data URL | 브라우저 생성 파일도 보호 또는 안전하게 차단 |
| D-05 | Service Worker | 중개된 응답을 보호하거나 명시적으로 차단 |
| D-06 | Content-Disposition | 원본 파일명·형식 안전 처리 |
| D-07 | 대용량 파일 | 메모리 전체 적재 없이 처리 |
| D-08 | 일시정지·재개 | 암호 스트림/부분 객체의 무결성 관리 |
| D-09 | 강제 종료·디스크 부족 | 부분 객체 복구/삭제 및 경고 |
| D-10 | 중복 파일명 | 내부 고유 ID, 외부 내보내기 충돌 처리 |

미지원 유형은 '지원'으로 표시하지 말고 실패를 명시한다.

## 금고 메타데이터

고유 파일 ID, 원래 파일명, MIME/확장자, 크기, 생성 시간, 출처(개인정보), 해시/무결성 태그, 다운로드 상태(대기/진행/완료/실패/손상), 암호 포맷 버전을 관리한다. 민감 필드는 암호화 인덱스에 둔다.

## 내부 열기와 내보내기

- **내부 열기:** PDF/이미지/텍스트 등 지원 범위는 후속 기술 검증과 안전한 렌더링 경계에 따라 결정. 미리보기에 사용한 원문이 영구 일반 디스크에 쓰이지 않도록 추적한다.
- **외부 열기:** 외부 앱의 일반 파일 요구와 임시 평문 생성 위험을 평가 후 구현. 안전을 검증하지 못하면 '내보내기 후 열기' UX만 제공한다.
- **내보내기:** 명시적 폴더 선택, 확장자 위장, Windows 예약 이름, `../` 경로 탐색, 파일 충돌, 중단, 복구, 무결성 오류 처리. 내보낸 평문은 금고 밖 보호 범위라는 안내를 1회 제공한다.
- **삭제:** 인덱스와 객체를 함께 정리하고 삭제의 물리적 복구 가능성(SSD/TRIM/백업)을 과장하지 않는다.

## UI 수용 기준

Ctrl+J에서 다운로드 진행률·일시정지/취소(지원 시)·열기·내보내기·삭제가 동작한다. 암호화 설정을 매번 묻지 않는다. 다운로드 불가 사유는 짧고 이해하기 쉬운 문구로 제공한다.

VEIL은 Ctrl+J에서 대기 및 전송 중인 항목별로 받은 용량과 취소 버튼을 표시한다. 전체 크기를 알면 진행 막대를 채우고, 알 수 없으면 받은 용량과 활동 표시를 보여 준다. 취소는 금고 발행이 시작되기 전까지 가능하며, 발행 단계에서는 버튼을 비활성화한다. 취소된 항목은 현재 브라우저 세션에서 상태만 표시되고 금고의 파일·암호화 목록에는 추가되지 않는다.

## Phase 4-0 실측 (2026-11-23)

범위는 [ADR-0004](decisions/ADR-0004-protection-policies.md) 5항이다. WebView2 157.0.4341.60, 개발 빌드, 호스트(일반 디스크의 합성 프로필)에서 시험했다.

### 확인한 엔진 제약

- WebView2에는 다운로드 바이트를 앱 스트림으로 넘기는 API가 없다. `DownloadStarting`이 발생할 때 엔진은 이미 응답 본문을 받기 시작했다. 작은 파일(1~4 KiB)은 본문 전체, 8 MiB는 약 1 MiB를 다운로드 임시 폴더에 기록한 뒤였다(64 MiB는 0). 이 폴더는 PR #3 이후 프로필의 `temp\downloads`(보호 볼륨)이며 취소 후 삭제되고 종료 시 비운다.
- 엔진은 받은 본문 앞부분을 **HTTP 디스크 캐시**(`Cache\Cache_Data`)에도 기록했다. 첫 시험에서 시험 페이로드가 캐시 파일에서 발견됐다. 다운로드를 취소할 때마다 디스크 캐시를 두 번(즉시, 1.5초 후) 비우도록 했고, 재시험 두 번에서 프로필의 모든 파일에 페이로드가 남지 않았다. 파일 시스템의 빈 공간에 남은 조각은 검사하지 않았다(보호 볼륨 안이다).

### 프로토타입 구조

```text
엔진 DownloadStarting → 즉시 취소, 엔진 캐시 비움
  ├ 미지원(http/https 아님, GET 아님, 금고 도구 없음) → 차단(평문 대체 없음)
  └ 지원(GET) → VEIL이 같은 URL을 다시 요청
        · 쿠키: 엔진 CookieManager에서 홉마다 조회(HttpOnly 포함), 리다이렉트는 직접 따라감(최대 10)
        · 시스템 프록시 미사용(보호 네트워크 경로는 Phase 5)
        → 64 KiB 프레임으로 veil-vault.exe 표준 입력에 전달(디스크에 평문 없음)
        → Rust 코어 age 스트리밍 암호화, 스테이징 후 원자적 발행
        → 종료 표시와 총 길이가 맞을 때만 발행, 아니면 스테이징 삭제
```

- `veil-vault.exe`(`crates/veil-security/src/bin/veil-vault.rs`): `init`/`seal`/`verify`. 단위 시험 3건 — 3 MB 정상 봉인·검증, 프레임 중간·경계에서 끊긴 스트림, 길이 불일치·잘못된 암호 모두 실패하고 **객체·스테이징 파일 없음**.
- 앱(`apps/desktop/DownloadVault.cs`): 세션마다 새 키링(메모리의 무작위 암호). **프로토타입 한계** — 앱 종료 후 객체를 열 수 없고, 메타데이터는 메모리에만 있으며, 내보내기·목록 UI는 아직 없다.

### 시험 결과 (`node tests/phase4/vault-capture.mjs`)

| 다운로드 | 결과 | 엔진이 취소 전 받은/기록한 바이트 |
|---|---|---|
| 1 KiB GET | 보관됨, 금고에서 인증 통과 | 1,024 / 1,024 |
| 8 MiB GET | 보관됨, 인증 통과 | 0 / 1,048,576 |
| 64 MiB GET | 보관됨, 인증 통과 | 0 / 0 |
| 쿠키 인증 4 KiB | 보관됨, 인증 통과 | 4,096 / 4,096 |
| 리다이렉트 후 2 KiB | 보관됨, 인증 통과 | 2,048 / 2,048 |
| 4 MiB 중 1 MiB 후 연결 끊김 | 실패, 객체 없음 | 0 / 0 |
| POST | 차단됨(미지원) | 2,048 / 2,048 |

- 종료 후 금고 폴더에는 키링과 보관된 객체 5개만 있었다. 프로필 전체 파일과 사용자 Downloads 폴더(파일 이름만 확인)에 시험 페이로드는 없었다.
- 기존 데스크톱 시험의 8가지 다운로드: GET·인증·리다이렉트·대용량은 보관됨, POST·Blob·Data URL은 차단됨, Service Worker는 실패(VEIL의 재요청은 네트워크로 가며 서비스 워커 응답을 받지 못한다). 어느 경우에도 평문 저장은 없다.

### 판단과 남은 위험

- **재요청 방식의 한계**: 같은 URL을 두 번 요청한다. 일회용 링크, 요청마다 달라지는 응답, 서버 측 다운로드 횟수 제한, 쿠키 외 인증(HTTP 인증 창, 클라이언트 인증서, 브라우저 세션 저장소 토큰)은 실패하거나 다른 결과를 받을 수 있다. 실패는 차단으로 끝나며 평문으로 우회하지 않는다. 실제 사이트에서의 성공률은 인터넷 VM 시험(ADR-0004 4항)에서 측정한다.
- **엔진 쪽 평문 조각**: 취소 전에 엔진이 받은 본문은 보호 볼륨의 임시 폴더와 캐시에 잠시 존재한다(삭제·비움 확인). 일반 시스템 디스크에는 기록되지 않는다(SEC-004 VM 추적). 금고 경로 전체의 볼륨 밖 쓰기는 VM Procmon 추적으로 다시 확인해야 한다.
- 후속 로컬 시험: 영구 키·복구·백업·내보내기와 항목별 진행률·취소 동작을 확인했다. 보호 볼륨 쓰기 추적과 디스크 부족·전원 차단 시험은 남아 있다. [보안 상태](SECURITY_STATUS.md#phase-4-영구-금고-로컬-검증-2026-11-23)

## Phase 6 다운로드 금고 UX 및 제한된 내부 미리보기 (구현·검증 보류)

- Ctrl+J의 기존 진행률·취소·결과 페이지를 유지하고 네이티브 금고 열기 버튼을 추가한다. Ctrl+Shift+J 및 설정의 기존 경로도 유지한다.
- 금고 관리 창에 파일명/출처 검색, 최신/오래된/이름/크기 정렬, 복구 항목 필터, 개별 인증 검사 및 총량 표시를 추가한다. 백업·전체 검사·암호/복구 코드/내용 키 교체는 금고 관리 메뉴로 이동한다. 작업은 창에서 직렬화하고 기존 vault gate를 사용한다.
- 내부 미리보기는 복구 항목이 아닌 256 KiB 이하 .txt에 한정한다. Rust 기존 read 명령으로 전체 인증 후 메모리에 반환하고 기록된 길이와 실제 길이를 비교한다. 엄격한 UTF-8 및 제어/방향 제어 문자 검사를 통과한 텍스트만 네이티브 TextBlock에 표시한다. HTML, PDF, 이미지, 실행 파일, 외부 앱, 임시 평문 파일은 사용하지 않는다. 파일 확장자만으로 신뢰 여부를 판단하지 않는다. 미리보기 바이트는 사용 후 지우지만 .NET 문자열·OS 메모리/덤프 삭제를 보장하지 않는다.
- 내보내기 전 금고 밖의 평문 저장을 안내하며 기존 파일 덮어쓰기를 허용하지 않는다. 예약 이름 및 잘못된 기본 파일명은 안전한 대체 이름을 사용한다. 실제 파일 발행은 기존 인증된 Rust export 경로를 사용한다.
- 항목 작업 전에 현재 금고의 ID/멤버십을 확인한다. 프로토콜 read 응답의 크기를 제한하며 잘못된 프레임은 세션을 종료한다. 삭제 및 인증 오류는 성공 또는 악성코드 판정으로 표현하지 않는다.
- **NOT RUN**: UI 및 smoke/VM 검증은 일괄 검증 단계에서 수행한다. 실제 데이터로 사용하기 전 보안 출시 게이트를 통과해야 한다.
