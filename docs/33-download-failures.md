# 33. Download failure handling (Stage 3-2)

- Fixed, non-secret diagnostics distinguish HTTP status, DNS/connection/proxy/TLS, vault open, storage permission/space, transfer interruption and uncertain finalization. No arbitrary exception messages in failure history.
- A fresh GET can be offered in the originating window's recent downloads popup only for an initial transient request error before any response body or vault publication; requires observed document GET in that tab, exact URI, same HTTPS origin, no query/fragment/credentials, same source and navigation epoch, unlocked vault and live tab. Memory-only candidate, at most one per window, five-minute expiry, dropped on navigation/close or context loss. No persistent retry URL. No automatic retry.
- Explicit confirmation consumes the candidate. Recheck after prompt and vault gate. Retry uses current cookies and configured proxy/threat policy; redirect on retry is refused, no retry chain or partial resume. GET is not guaranteed idempotent; the user must consent. Unknown request method, tokens, authentication failures, TLS failures, blocked threats, transfer/storage/commit failures and private mode do not offer retry. Reopen original page to request again.
- Existing capture eligibility remains unchanged for compatibility; the extra restrictions apply to retries. Existing download scratch/write-trace and redirect-policy limitations are not resolved by this change.
- Rust encryption protocol unchanged. Synthetic policy smoke added; Windows actual HTTP fixture failures, retry/expiry/context races, disk-full and commit recovery NOT RUN. No release gate change.
