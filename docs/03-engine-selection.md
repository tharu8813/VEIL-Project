# 03. 브라우저 엔진 기술 검증 및 선정

## 결론은 아직 미확정

**[검증 필요]** 초기 생산성 때문에 Python + PySide6 + Qt WebEngine을 우선 PoC 후보로 고려한다. 단, 프로필 암호화와 다운로드 스트림 제어 요구를 충족하지 못하면 CEF/Chromium 수정 또는 다른 검증된 아키텍처로 전환한다. 사용자용 엔진을 미리 확정하지 않는다.

## 비교 대상

1. Python + PySide6 + Qt WebEngine
2. C++ + Qt WebEngine
3. CEF (Chromium Embedded Framework)
4. Chromium 소스 포크/커스텀 빌드
5. Microsoft WebView2

## PoC 실험 순서

### E-01. 로그인/사이트 데이터 지속성

로컬 테스트 서버에서 쿠키, IndexedDB, LocalStorage 및 Service Worker/CacheStorage를 저장한다. 정상 종료→재실행 및 비정상 종료→재실행을 구분하여 복구를 확인한다.

### E-02. 프로필 디스크 기록

테스트 전용 문자열, 쿠키 값, DB 값, 캐시 응답을 사용하여 파일 핸들·쓰기 경로를 조사한다. 앱 데이터 폴더, `%TEMP%`, crash/log 경로, 프로세스 하위 구성 요소의 쓰기를 조사한다.

### E-03. 다운로드 경로 제어

일반 GET·인증·POST·리다이렉트·Blob·Data URL·Service Worker 파일·대용량을 각각 실행한다. **다운로드 완료 후 암호화는 불합격**으로 기록한다.

### E-04. 누출/샌드박스 조사

프록시·DNS 장애 중 연결 우회, IPv6, WebRTC, QUIC을 검사한다. 렌더러 샌드박스 적용 여부도 확인한다.

### E-05. 업데이트 및 공급망

보안 수정 반영 시간, 이슈 대응 가능성, 릴리스 자동화 가능성을 확인한다. Chromium을 직접 포크하는 경우 누적 패치 적용 비용을 반드시 평가한다.

## 의사결정 규칙

- 비교 표에 **가능/제한적/불가/미검증** 중 하나와 **근거 링크·시험 기록**을 붙인다.
- 절대적인 보안 요구를 우회하지 않는 엔진을 우선한다.
- 어떤 엔진도 핵심 요구를 충족하지 못하면 **정식 배포 범위를 축소/보류**하고 사실을 보고한다.
- `docs/decisions/` 하위에 ADR(선택·대안·근거·포기 비용·재평가 조건)을 만든다.

## 참고 문서 시작점 (실제 버전 확인 필수)

- Qt WebEngine `QWebEngineProfile`, `QWebEngineDownloadRequest`, `QWebEngineCookieStore` 공식 문서
- CEF API 및 Chromium upstream 소스/보안 업데이트 문서
- WebView2 사용자 데이터 폴더 및 다운로드 API 문서
- Chromium 네트워크/스토리지/샌드박스 아키텍처 문서

문서만 읽고 실증하지 않은 결과는 '자료상 가능'으로 기록한다.
