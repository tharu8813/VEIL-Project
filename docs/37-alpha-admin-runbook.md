# 37. Internal Alpha 관리자 런북

상태: 절차 초안 및 코드 대조 완료, 실제 Windows/BitLocker VM 실행 **NOT RUN**. ADR-0010의 합격 기준이나 배포 승인을 변경하지 않는다. 최초에는 폐기용 합성 계정과 격리 VM에서만 실행한다.

## 1. 내부 서명 인증서와 별도 신뢰 경로

- 릴리스 관리자는 승인한 소스 커밋, 버전, 채널, 서명 인증서 주체/발급자/유효 기간, Windows 인증서 지문(40자리), 인증서 DER 파일의 SHA-256을 릴리스 기록에 남긴다. 인증서 공개 사본만 전달하고 개인키/PFX/비밀번호는 절대 배포하지 않는다.
- 패키지와 인증서 지문을 같은 다운로드 위치에 올리는 것만으로는 신뢰 경로가 되지 않는다. 지문과 SHA-256, 승인 버전 및 커밋을 미리 확인된 관리자 연락 경로 또는 별도의 인증된 관리 채널로 제공한다. 수신 관리자는 해당 기록을 독립적으로 확인한다.
- 유지보수 스크립트 역시 승인된 소스 커밋에서 취득해 관리자 쓰기 전용 경로에 보관하고 검토한다. 패키지에서 나온 스크립트를 실행하지 않는다.
- Windows 관리자 PowerShell 5.1에서 공개 DER 인증서 파일을 검사하는 예시(실제 경로와 승인 값은 별도 기록에서 가져온다):

```powershell
$certFile = 'C:\AdminTools\veil-alpha.cer'
$cert = [Security.Cryptography.X509Certificates.X509Certificate2]::new($certFile)
$cert | Select-Object Subject,Issuer,NotBefore,NotAfter,Thumbprint
Get-FileHash -LiteralPath $certFile -Algorithm SHA256
```

두 지문과 승인된 인증서 정보가 일치하지 않거나, 기간이 만료됐거나, 신뢰 경로가 확인되지 않으면 중단한다. 내부 인증서 신뢰 등록은 관리자 조직 정책에 따른다. 검증을 위해 임의 인증서를 실제 호스트의 루트 저장소에 추가하거나 Authenticode/CMS 검사를 끄지 않는다. VM 시험용 인증서는 격리 VM에만 신뢰 등록하고 운영 서명에 재사용하지 않는다.

승인된 40자리 지문을 `package-maintenance.ps1 -SignerThumbprint`로 전달한다. 이 값은 패키지의 manifest에서 복사하지 않는다. 스크립트는 CMS 체인과 서명자, 정확한 파일 목록·SHA-256·길이 및 실행 파일 Authenticode를 검사한다. 서명 실패 시 다른 지문으로 재시도하지 않는다. 새 인증서로의 키 회전과 신뢰 폐기는 별도 정책/구현이 필요하며, 현재 업데이트에서 자동으로 허용하지 않는다.

## 2. 재설치 및 재등록 사전 점검

대상은 정상 제거 후 남은 보호 VHDX/등록 또는 보호기 변경 이후의 복구다. 중단된 업데이트는 먼저 기존 `-RecoverInterruptedUpdate` 경로로 처리한다. 손상된 저널, 출처 불명 등록, 분리 실패, 복구 키 불일치는 작업 중단 조건이다.

1. 기존 VEIL 창과 금고 작업을 정상 종료한다. 브로커 서비스를 중지하고 VHDX가 잠겼으며 분리됐는지 확인한다. 강제 종료, 평문 폴백, 연결된 이미지 복사는 금지한다.
2. 관리자만 쓸 수 있는 별도 보호 위치에 원본 VHDX의 오프라인 사본과 기존 `%ProgramData%\VEIL` 등록 파일(ACL 포함)을 보존한다. 사본의 SHA-256 및 원본과의 일치를 확인한다. 등록 JSON은 공개 로그에 올리지 않는다. 기존 서명 패키지 및 신뢰 기록도 보관한다.
3. 기존 등록에서 imagePath, volumeGuid, protectorId, recoveryProtectorId, userSid, profilePath, volumeId, 기존 clientSha256을 대조한다. 파일 경로와 SID는 신뢰된 등록 및 Windows 실제 볼륨 정보에서 교차 확인하며 추측하지 않는다.
4. 기존 서비스가 설치돼 있고 중지됐으면 관리자 도구 `broker-service.ps1 -VerifyRecovery`로 외부 보관 복구 사본을 검사한다. 복구 암호는 입력 창에만 넣는다. 서비스가 이미 제거되었으면 이 명령을 실행할 수 없으므로 별도 격리 사본에서 Windows BitLocker 복구 드릴을 수행한다. 검증 후 볼륨을 다시 잠그고 분리한다.
5. 보호기 변경이 필요하면 기존 복구 사본을 검증한 후 격리 사본에서 Windows BitLocker 절차로 변경한다. 새 보호기 ID를 기록하고 새 복구 사본 검증 전 기존 복구 보호기를 제거하지 않는다. 금고 복구 코드 및 별도 비밀번호 관리자 정책은 BitLocker와 독립이다.

## 3. 재등록 리허설 (격리 VM 전용)

현재 `package-maintenance.ps1 -Remove`는 서비스 및 바이너리만 제거하고 등록과 VHDX를 보존한다. 남은 등록이 있으면 `-Install`은 의도적으로 거부한다. 재등록 전용 트랜잭션은 아직 없다.

- 격리 VM에서만, 2절의 검증된 오프라인 백업을 확보하고 관리자 승인 아래 기존 등록 정리 경로를 평가한다. 레거시 `broker-service.ps1 -Remove`는 등록까지 삭제하므로 정상 제거의 대체 수단이 아니다. 원본 실사용 시스템에서는 이 런북만으로 실행하지 않는다. 유지보수와 레거시 도구를 동시에 실행하지 않는다.
- 정리 후에만 승인된 서명 패키지로 `package-maintenance.ps1 -Install`을 실행하는 리허설을 한다. `Package`, `SignerThumbprint`, `ImagePath`, `ProfilePath`, `VolumeGuid`, `ProtectorId`, `RecoveryProtectorId`, `UserSid`에는 검증된 값을 사용한다. 설치기는 새 volumeId를 발급한다. 기존 데이터가 새 등록에서도 읽히는지는 실측할 항목이며 보장하지 않는다.
- 실제 복구 키를 다시 확인하고 일반 사용자 Release 앱에서 프로필을 열어 합성 북마크·쿠키·기록·금고 파일과 인증을 비교한다. 보호 프로필 암호 변경으로 금고 인증이 실패하면 기존 금고 암호 또는 금고 복구 코드 경로를 사용한다. 비밀번호 관리자 암호 분실은 복구할 수 없다.
- 정상 종료, Windows 잠금, 강제 종료 후 재잠금 및 VHDX 분리를 확인한다. 새 등록의 복구 드릴을 수행한 뒤에만 리허설 완료로 기록한다.
- 실패하면 서비스와 브라우저를 중지하고 볼륨을 잠가 분리한다. 원본 백업을 덮어쓰거나 등록 JSON의 해시/ID를 수동으로 조작하지 않는다. 격리 사본을 보존해 원인을 확인하고 재현한다. 실제 재등록 자동화와 장애 복구 설계는 별도 검토 대상이다.

## 4. 증거와 중단 조건

| 확인 항목 | 현재 |
|---|---|
| 별도 채널 인증서 전달·지문 확인 | 절차 작성, NOT RUN |
| 정상 제거 후 기존 등록 보존 | 실제 VM NOT RUN |
| 재등록 후 프로필 및 금고 복원 | NOT RUN |
| 복구 보호기 변경·복구 드릴·재잠금 | NOT RUN |
| 재등록 중단 시 원본 보존 | NOT RUN |

증거에는 시험 날짜, 소스 SHA, 패키지 버전, 시험 인증서 공개 지문, 단계별 PASS/FAIL/NOT RUN, 비밀 없는 오류 분류 및 증거 경로만 기록한다. 복구 암호, 금고 코드, 사용자 데이터는 포함하지 않는다. 어느 한 단계라도 실패하면 Alpha 출시 승인을 하지 않는다.
