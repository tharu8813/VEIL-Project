# ADR-0006 네트워크 보호 1단계: 표준 보호와 프록시 보호 모드

- 상태 — 채택(1단계 구현). OS 수준 강제(WFP)와 VM 누출 시험은 후속.
- 작성일 — 2026-11-23
- 관련 — [08 네트워크 보호](../08-network-guard.md), SEC-009, SEC-010, Gate D, ADR-0004·0005

## 배경

Phase 0에서 WebView2에 고정 프록시(`--proxy-server`, 폴백 없음)를 주면 프록시 장애 시 HTTP 요청이 직접 연결로 새지 않는 것을 확인했다. 앱에는 네트워크 모드가 없었다. 다운로드 금고(ADR-0005)는 VEIL이 자체 HTTP 클라이언트로 파일을 다시 받는데, 이 클라이언트는 프록시를 쓰지 않도록 고정되어 있어 보호 모드가 생기면 직접 연결로 새는 경로가 된다.

## 결정

### 모드와 저장

- 모드는 **표준 보호**(기본)와 **프록시 보호** 두 가지다. 설정은 앱 상태 파일(보호 볼륨)에 저장하고, 엔진 시작 인수에 반영되므로 **다시 시작한 뒤 적용**된다. 화면은 `선택됨`(저장, 재시작 필요) · `적용됨`(이번 실행의 엔진에 반영) · `경로 검증됨`(프록시에 실제 연결 성공) · `차단됨`(프록시 연결 실패, 직접 연결 없음)을 구분한다.
- 프록시는 `http` 또는 `socks5` 한 개, 호스트와 포트만 받는다. 사용자 이름·암호가 필요한 프록시는 이번 단계에서 지원하지 않는다(자격 증명 저장을 피함).

### 표준 보호

- **HTTPS 우선** — 사용자가 연 링크나 입력한 주소가 `http://`이고 대상이 루프백·사설·`.local`·`.test` 주소가 아니면 `https://`로 바꿔 연다. HTTPS 연결이 실패하면 경고 페이지를 보여 주고, 사용자가 명시적으로 고른 경우에만 그 호스트를 이번 실행 동안 HTTP로 연다. 하위 리소스의 혼합 콘텐츠는 엔진 기본 차단을 따른다.
- **추적 방지** — 엔진 추적 방지 수준을 Strict로 둔다. 호환성 문제는 인터넷 VM 시험에서 기록한다.
- 실제 IP 은닉을 표시하거나 약속하지 않는다.

### 프록시 보호 (실패 시 차단)

- 엔진 인수: `--proxy-server=<scheme>://<host>:<port>`, `--proxy-bypass-list=<-loopback>`(루프백도 프록시로), `--webrtc-ip-handling-policy=disable_non_proxied_udp`(WebRTC가 프록시를 거치지 않는 UDP를 쓰지 않음), `--disable-quic`. PAC·자동 감지·`DIRECT` 폴백은 쓰지 않는다.
- **VEIL 자체 요청**(금고 재요청)은 같은 프록시만 사용한다. 프록시 설정이 없거나 연결되지 않으면 요청하지 않는다.
- 시작할 때 프록시 주소로 TCP 연결을 시험해 `경로 검증됨` 또는 `차단됨`을 표시한다. 연결 시험은 경로 표시용이며, 차단 자체는 엔진 인수(폴백 없음)에 의존한다.

### 보안 DNS (2단계, 2026-11-23)

- WebView2에는 보안 DNS API나 명령줄 스위치가 없다. 런타임(157.0.4341.60)에 Chromium 보안 DNS 환경설정(`dns_over_https.mode`, `dns_over_https.templates`)이 있음을 확인했고, 엔진 시작 전에 엔진 Local State에 쓰면 적용되는 것을 실측했다.
- 설정은 네트워크 보호의 일부(`DnsTemplate`)다. 시스템 DNS(보호 안 함), Cloudflare·Quad9·Google, 직접 입력한 `https://` 템플릿 중 고른다. 선택하면 `mode=secure`로 써서 DoH 실패 시 시스템 DNS로 되돌아가지 않는다. 기존 Local State의 다른 값은 보존한다. DoH를 요청했는데 적용할 수 없으면 시작을 거부한다. 시스템 DNS로 돌리면 VEIL이 쓴 값만 지운다.
- 공개 DoH 서버 이름은 엔진이 시스템 DNS로 한 번 찾을 수 있다(부트스트랩). 이 경우 노출되는 것은 DoH 제공자 이름뿐이다(VM에서 확인 예정).
- 프록시 보호 모드에서는 이름 해석을 프록시가 맡는다. 보안 DNS 설정은 그대로 두되 효과는 VM에서 확인한다.
- 시험용으로만 Debug 빌드에 `VEIL_TEST_TRUSTED_SPKI` 훅을 둔다. 지정한 시험 인증서 키 하나를 신뢰하게 하는 엔진 인수이며 Release 바이너리에는 포함되지 않음을 확인했다.
- 실측(호스트): 로컬 DoH 응답기로 합성 이름이 해석되어 페이지가 열렸고, 응답기를 멈추면 해석이 실패했다(시스템 DNS 폴백 없음). 엔진은 배경에서 `config.edge.skype.com`(Edge 원격 구성)과 `nav-edge.smartscreen.microsoft.com`(SmartScreen 평판 검사)도 DoH로 조회했다. SmartScreen은 방문 주소를 Microsoft에 보내므로 끌지 여부는 보안·개인정보 절충으로 별도 결정한다.

### WebRTC 스위치 수정 (2026-11-24)

- 결함: 1단계에서 넣은 `--force-webrtc-ip-handling-policy`는 Chrome 전용 스위치다. WebView2 런타임(157.0.4341.60) `msedge.dll`에는 이 문자열이 없어 **무시됐다**. 프록시 보호 모드에서도 WebRTC가 UDP host 후보(mDNS로 가린 `.local` 주소)를 수집했고, STUN 서버가 있으면 실제 IP가 드러날 수 있는 상태였다.
- 1단계 시험은 엔진 명령줄에 인수가 있는지만 확인했고, 효과는 확인하지 않았다.
- 수정: 런타임이 지원하는 `--webrtc-ip-handling-policy`로 바꿨다. 같은 조건에서 표준 모드는 UDP 후보 1개, 프록시 모드는 후보 0개로 확인했다.
- 회귀 시험 `tests/phase5/webrtc-guard.mjs`를 추가했다. 루프백 전용이며 STUN이나 외부 연결을 쓰지 않는다.
- 나머지 엔진 스위치(`--proxy-server`, `--proxy-bypass-list`, `--disable-quic`, 시험용 SPKI)는 런타임 문자열에 있음을 확인했다. `--disable-quic`의 실제 효과는 인터넷 VM에서 확인한다.

## 검증

- 로컬 자동 시험: HTTPS 우선 판정과 경고 페이지, 추적 방지 수준, 엔진 명령줄의 프록시·WebRTC·QUIC 인수, 프록시 경유 탐색과 금고 다운로드, 프록시 중단 후 탐색·금고 다운로드 모두 원 서버에 직접 요청 없음.
- **NOT RUN(통합 VM)**: 실제 DNS 질의 경로, 외부 IPv6, WebRTC 실제 ICE 후보, 절전·재개 및 네트워크 전환 중 우회, 엔진 외 프로세스(업데이트·진단)의 직접 연결.

## 결과와 열린 항목

- 프로세스 밖에서 강제하는 장치가 없으므로 엔진 버그나 엔진이 아닌 구성 요소의 직접 연결은 막지 못한다. 고강도 보호를 표시하기 전에 WFP 강제를 별도 ADR로 검토한다.
- SOCKS5에서 이름 해석이 프록시 쪽에서 일어나는지는 VM에서 DNS 추적으로 확인한다.
- Tor 모드는 이번 범위가 아니다.
