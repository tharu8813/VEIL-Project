# CEF authenticated system module baseline (P2-03)

Status: disconnected verifier and synthetic regression implementation; not a product admission mechanism.

The exact UTF-8 JSON payload is signed separately with RSA-PSS/SHA-256 using a 3072- or 4096-bit key. The schema is `veil-cef-system-modules-v1`, architecture is `x64`, and the document includes integer Windows build, updateRevision, sequence and a modules array. Each entry contains name, bytes, sha256 and signerSha256. The verifier refuses duplicate/unknown/missing fields, invalid module pins and case-insensitive duplicate names; the payload is limited to 1 MiB and 1024 modules.

The trusted public SPKI, expected host identity and minimum allowed sequence are independent inputs. Never accept a key from this document, derive the baseline from observed CEF modules, or trust the document's host/sequence as the comparison values. A valid signature does not establish OS provenance or the trustworthiness of the source manifest.

- Read-only installed trust reader: fixed HKLM 64-bit SOFTWARE\VEIL.CefSystemBaselineTrust, exact protected owner/DACL, no links or user-hive fallback, one binary TrustRecord. Format: VEILBST1 (8 ASCII), positive minimum sequence (LE int64), exact payload SHA-256 (32 bytes), SPKI size (LE int32), RSA SPKI. The exact digest prevents same-sequence substitution. VerifyInstalledTrust rechecks the snapshot around verification and inventories. Synthetic tests only; actual registry provisioning/ACL/link races NOT RUN.
- Prepared enrollment/update policy: enrollment requires an independently supplied SHA-256 SPKI anchor and minimum sequence; replacement uses only the existing key and requires a strictly higher authenticated sequence. The installed record stores the exact signed sequence (not an arbitrary lower floor); readers refuse mismatches. Prepared records check the expected previous state and host immediately before a future write, and compare the published record afterward. Ordinary replacement cannot rotate keys or implicitly enroll.
- Separate prepared key rotation: a different RSA modulus must sign the new baseline at a strictly higher sequence. Independent release authorization must supply a detached RSA-PSS/SHA-256 signature (SignHash, not SignData) of SHA256(ASCII domain VEIL-CEF-BASELINE-KEY-ROTATION-V1 || SHA256(old complete TrustRecord) || SHA256(new complete TrustRecord)). The digest binds the precise transition, including the new key and payload; a raw digest is no longer accepted. Old-key approval is deliberately insufficient for compromise recovery. A published replacement removes old-key acceptance from the current record. No global revocation list or independent authorization transport is implemented. A compromised old key can still sign ordinary updates until a revocation or rotation is published; sequence exhaustion, privileged rollback and compromised release authority require separate recovery policy.

Preparation requires an independent RSA-PSS/SHA-256 signature (SignHash) of SHA256(ASCII domain VEIL-CEF-BASELINE-KEY-REVOCATION-V1 || SHA256(exact installed record)); no compromised-key signature is needed. Revoked records refuse installed baseline use and ordinary updates; prior active verifiers reject a changed record at the next guard check. Recovery requires separately approved exact-record key rotation to a different RSA modulus and a higher sequence. No deletion, automatic re-enrollment, production IPC/startup integration or live process termination. The old binary parser rejects the new magic. Actual publication, emergency shutdown latency and rollback of the entire record remain unverified/outstanding.
